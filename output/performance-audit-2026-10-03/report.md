**Website performance audit — 3 October 2026**

The largest opportunities are removing the mandatory animated loading screen, showing the Home content before its logo finishes, and reducing mobile startup/rendering work in People and the Nucleus Ride. Desktop page loading is healthy with hardware acceleration. The animated views need separate measurement: the Experiences landing score does not include opening the Ride, and Home's measured largest-content element is the navigation brand rather than the animated hero.

This audit used a fresh production SSR build, an isolated in-memory copy of the repository's public seed data (three published event records and fifteen members), and Chromium 153.0.8010.12 with Intel UHD Graphics through D3D11. Desktop viewport: 1440 × 900. Mobile viewport: 390 × 844, DPR 3. Lighthouse mobile results use its simulated slow-4G profile and 4× CPU slowdown. Runtime observations use real hardware rendering, local networking, and 4× CPU slowdown for the mobile profile. The monitor runs at 144 Hz; emulated mobile results are not physical-phone FPS measurements.

The measured build includes `index-iqgFDlwM.js`, `three-Cb8aZj6Z.js`, `people-tower-Dn0msb0h.js`, and `EventRollercoaster-CgEnf3Cc.js`. Source changes from other ongoing work appeared during the audit; these measurements describe this production build, not subsequent source edits. No application code was changed for this audit.

1. **Highest return: the loading screen delays every public page.** It preloads and decodes seventeen 1440 × 810 WebP frames totaling 491,796 bytes. That is about two thirds of the approximately 728–763 KB transferred by the simpler pages. The images have a theoretical uncompressed RGBA footprint of 79.7 MB / 76 MiB; this is a decoded-size estimate, not a measured memory allocation. The waterfall shows seventeen unique assets with additional cache hits, not thirty-four full downloads. The app deliberately holds the overlay for at least 1.4 seconds after startup, followed by a 350–450 ms exit. In local runtime measurements the page became unlocked around 2.1 seconds on desktop and 2.3–2.5 seconds on the mobile profile, despite much earlier server content. Remove the blocking intro, or use one small static mark and reserve the animation for an explicit introduction. Removing all seventeen images avoids approximately 492 KB on a cold load; retaining the first frame would save approximately 454 KB. 2. **Home delays its real message and keeps drawing on desktop.** The main hero text is gated on completion of the logo reveal. It became eligible to appear at 5.92 seconds on desktop and 6.57–6.60 seconds on mobile over localhost; a 900 ms text entrance follows. The logo starts after the page loader, so the two waits accumulate. Lighthouse's Home LCP is the small “NUCLEUS” navigation brand, which hides this delay in the headline score. Show the hero text and a static logo immediately, then run the formation as an enhancement. Precompute the logo contour at build time instead of scanning image alpha and generating the contour on every fresh scene. After formation, the desktop scene still submitted about 144 renders per second on this monitor, while the mobile scene correctly stopped. Let the desktop scene sleep after formation and wake on pointer movement/resize, or cap its decorative updates. Sources: [LogoLanding.tsx](C:/Users/ryan1/OneDrive/Documents/club-website/src/components/home/LogoLanding.tsx:12), [App.tsx](C:/Users/ryan1/OneDrive/Documents/club-website/src/App.tsx:157), [logo-scene.ts](C:/Users/ryan1/OneDrive/Documents/club-website/src/lib/logo-scene.ts:81), [logo-scene.ts](C:/Users/ryan1/OneDrive/Documents/club-website/src/lib/logo-scene.ts:367).

3. **People has the weakest mobile startup.** Its repeated mobile LCP is approximately 5.44 seconds. The initial scripts total about 1.10 MB uncompressed / 329 KB transferred, including Three.js and the physics/tower bundle. The measured LCP element is the interaction hint, which only appears once the 3D scene is ready. Tower setup creates geometry, canvas textures, physics, and CSS3D profiles before readiness; local mobile startup contained a 246 ms long task. A static member presentation should be readable before this work completes, with the tower loaded afterward or on request. Precompute reusable geometry/textures and profile setup separately from first paint. During mobile swipes, style recalculation consumed about 1.13 seconds over a five-second sample, making repeated profile opacity/transform updates a secondary optimization target. Cache unchanged style values and update only the moving profile. The scene already uses only about five draw calls, turns off mobile shadows, and sleeps when a profile settles; do not replace these existing optimizations with broader rewrites. Before offering a lightweight/reduced-motion mode, restore actual member content in the fallback: the inspected People component currently renders the scene and HUD without a static roster. Sources: [PeoplePage.tsx](C:/Users/ryan1/OneDrive/Documents/club-website/src/pages/PeoplePage.tsx:35), [people-tower.ts](C:/Users/ryan1/OneDrive/Documents/club-website/src/lib/people-tower.ts:51), [people-tower.ts](C:/Users/ryan1/OneDrive/Documents/club-website/src/lib/people-tower.ts:246).

4. **The Ride is the largest interactive CPU/rendering workload.** Opening it took approximately 2.28 seconds on the mobile CPU profile and 1.48 seconds on desktop. Mobile startup contained 933 ms and 471 ms long tasks. While driving, the mobile profile spent 4.46 of 4.51 seconds in main-thread tasks, including 3.64 seconds of scripting; its 95th-percentile frame interval was 20.8 ms, beyond a 60 Hz frame's 16.7 ms budget. Recorded scene draw counts varied around 63–104 per rendered frame. At the tested quality level it also renders through an offscreen target and a fullscreen postprocessing pass. `rideQuality()` receives a coarse-pointer hint but bases its initial/max quality only on cores and memory; those hints do not reliably identify a weak phone GPU. Start more conservatively on constrained touch devices, disable bloom/depth effects until the device demonstrates sufficient headroom, reduce distant scene detail and draw submissions, and split synchronous setup into smaller steps. `compileAsync` before the first reveal is also worth evaluating; it will not eliminate geometry-generation work. The animation scheduler continues ticking with dialogs open even when GPU rendering can stop, so stop that loop after transitions settle and wake it on state/input changes. Sources: [event-quality.ts](C:/Users/ryan1/OneDrive/Documents/club-website/src/lib/event-quality.ts:4), [event-world.ts](C:/Users/ryan1/OneDrive/Documents/club-website/src/lib/event-world.ts:17), [event-world.ts](C:/Users/ryan1/OneDrive/Documents/club-website/src/lib/event-world.ts:450), [event-postprocessing.ts](C:/Users/ryan1/OneDrive/Documents/club-website/src/lib/event-postprocessing.ts:74).

5. **Quick Browse does animation work for all seven cards.** Each card creates six spring-driven values, plus one shared progress spring: forty-three springs for seven pages. The mobile swipe sample used about 3.38 seconds of main-thread time over five seconds, with a 20.7 ms 95th-percentile frame interval. Desktop's corresponding interval was 13.8 ms. This is a secondary bottleneck rather than a broken carousel. Keep all seven pages, but activate the artwork/parallax only for the visible card and its neighbors; use a simpler transform sequence on narrow touch screens. Preserve the scroll-snap positions and navigation while suspending animation subscriptions for distant cards. Source: [EventCarousel.tsx](C:/Users/ryan1/OneDrive/Documents/club-website/src/pages/EventCarousel.tsx:40).

6. **The shared entry bundle can be made leaner.** The build's main entry is about 437 KB uncompressed / 141 KB gzip; Three.js adds about 531 KB / 136 KB gzip where needed. Lighthouse estimates roughly 67 KiB of startup-unused JavaScript on the simpler pages and 146 KiB across the People page's scripts. These are coverage estimates, not proof that the code can be deleted: some is required by later interactions. Profile the shared entry's module composition, move Home-only components into a Home route chunk, and use smaller animation entry points where appropriate. The existing route splits are valuable: loading Experiences does not automatically load its Ride, and the other public route chunks stay deferred. Sources: [App.tsx](C:/Users/ryan1/OneDrive/Documents/club-website/src/App.tsx:13), [route-pages.tsx](C:/Users/ryan1/OneDrive/Documents/club-website/src/route-pages.tsx:1).

The results also show useful strengths. Member photos are lazy: none transferred during the initial People Lighthouse run, and they appeared as profiles were visited. Mobile Home and settled People views stopped GPU submissions. Static assets are compressed and cached, layout shift was negligible, and `/api/site` responses were around 3–4 ms over loopback with this small dataset. Server-rendered Home responses took roughly 75–127 ms in one sample, so there is some server/rendering overhead, but it does not explain the multi-second foreground delays. Production hosting, database growth, concurrency, and real-user INP were not measured.

The first browser pass used SwiftShader software graphics and made desktop People look much worse. Those results are retained in the parent directory for transparency and excluded from the conclusions above. Hardware-accelerated reruns produced the table in this report. Lighthouse's back/forward-cache warnings came from browser automation launch flags and are also excluded as website defects. Early runtime attempts used a development-only Ride diagnostic selector and a synthetic touch gesture that did not scroll; those attempts were replaced with production-ready selectors and dispatched touch events. Only successful corrected samples appear in `runtime-verified.json`.

Recommended implementation order: remove the blocking loader and reveal Home content immediately; make People readable before WebGL; reduce Ride setup/mobile quality cost; then tune Quick Browse and the shared bundle. Recheck the same cold-load and interaction scenarios after each change, and validate the 3D views on a real Android phone and iPhone before drawing device-level FPS conclusions.
